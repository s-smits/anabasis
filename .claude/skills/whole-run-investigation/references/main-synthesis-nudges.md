# Main synthesis: judgement nudges

Use this when turning the deterministic read and the lane reports into `main_synthesis.md`. It
guides the primary reviewer and adds no gate and no campaign authority. Read the parts that matter
to this run rather than performing every investigation it mentions; the aim is to settle the
decisions the evidence can settle and then deliver the rest honestly.

## Start from the operator's decision

Ask first what the operator is trying to decide once the review is done. It is usually whether the
product works, what limited it, what changed, or which repair is worth trying, and that question
should order the synthesis rather than the order the reports happened to arrive in. Keep the exact
one-line request in view throughout, because a convenient generated subproblem can underserve it,
and never quietly turn a request for broader capability into a search for a higher score.

Begin with the measured source identity and [the checklist](../CHECKLIST.md), then give the
consequential conclusion in ordinary language with its strongest evidence beside it. Say what a
capable user can rely on and the specific condition that still limits that. "Not universally
proved" is rarely a finding; name the concrete missing or adverse evidence instead. One credible
counterexample settles a defect without an estimate of its prevalence, and a finite set of
successful cases supports a bounded capability without promising every use.

## Weigh what the Builder wrote

The measured battery is the Builder's own exam, so before a pass rate enters the synthesis, say
how much of what produced it the Builder did not write. The tasks, the limits, the checks, the
controls, the reference and the solver's tools all came from one session, and the host verifier's
authority is over the verdict, not over whether the check observes the property the request cares
about. So a pass can mean an easy task, a check that observes too little, or both. Say which of the
three this run's evidence can separate, and where it cannot, say that plainly rather than picking
the reading that flatters the run.

Rank the verdicts by independence. A pass lane 35 recomputed from public facts outweighs one only
the Builder's check produced; an installed external tool deciding a check outweighs an authored
algorithm run through an installed interpreter, which remains authored computation whatever it
runs on; and a verdict whose tool digest no longer resolves rests on an unestablished instrument.
Name the recorded tool source and digest behind each capability sentence, because a reader who
cannot tell which bytes decided a pass cannot tell what the pass means.

Earlier investigations reached diagnoses about where this system's weakness sits. Carry each one
into this synthesis as a question with the lane that tests it, and answer it from this run's bytes:
observed, inferred, or not established. A diagnosis that was right for one run is still a
hypothesis for the next.

## Recover before restarting

Check the existing manifests, report files, snapshots and session terminals before paying for
another review, since a resumed session should finish the accepted work rather than rerun it all
after a compaction. Retain complete reports, including opinions later rejected, under the archive
contract. A recovered report is not a verified transport identity and not a still-running session;
missing transport receipts limit provenance without erasing the primary evidence you can still
inspect, and a session id or a clean process exit does not supply a report that is missing.

Do the deterministic joins once, in the primary session, with the owning readers, and use
subagents only where a bounded judgement benefits from independence. Keep the two sides of an
independent challenge apart until both return. If a lane is missing, name the missing work, and
replace only the coverage that still affects the decision. An older note naming a lane by a retired
number is carrying a mechanism; translate the mechanism to whichever of the thirty-eight lanes owns
it today. The skill and the archive validator own the required shape, and this reference invents
no other.

## Bind the evidence that decides

Read the opening's full source SHA and keep it apart from the analyst's and the procedure's
revisions. Follow the saved candidate, the accepted snapshot, the executed bundle and the task-set
identities. Workspace Git is attribution, not a substitute for the bytes that were accepted and
run, and a later file with the same name can describe a different harness generation. When a live
run advances, refresh what it affects and keep the findings whose identities still match.

Keep operational closure apart from capability, and partition verified, unaccepted and typed
non-result cases before any rate is reported. Readers disagree about this more than they should: a
claim's `n`, the climb history's `n` and an exporter's rate can all count unaccepted cases as
scored, so recount through the classifier before quoting any of them. A pre-submit stop can leave
substantial work on disk and still have no measured harness, an environment terminal can be
informative without becoming a failed solution, and a signal or quota stop erases no verdict
recorded before it.

Put the denominator beside each inference rather than in a distant accounting section. Cases,
batteries, author calls, submits, completed rounds and provider units are different things. Treat
an unavailable cost, model identity or opportunity as unknown rather than zero, and when an archive
field cannot express a fact, say so rather than invent a receipt. A well-formed archive does not
stand in for a sound conclusion.

## Find the consumer, not only the calculation

For a consequential claim, follow the short path from the input bytes to the deciding output: what
receives the artifact, what computes the result, and what the controller finally consumes. Look for
filtering, projection, substitution and applicability between those points, since an evaluator can
reject while a later deciding predicate accepts. A prompt assertion, a type or a helper test proves
only the layer it reaches, so ask whether the report exercised the consumer that made the recorded
decision.

Consider a legitimate division of authority as seriously as a defect. Generated diagnostics can be
advisory by design while a host check owns correctness, and then the fix is the declaration or
binding rather than new authority for the diagnostics. Check callers before naming one owner,
because a local symptom may have a single shared producer, and stop tracing once you can name the
deciding line, its contract and the decision it affects.

If a cheap replay can separate two explanations, run it in private scratch against the measured
layer, using the recorded public input and accepted artifact where they fit, and pair the hostile
probe with a positive control so the result means something. A counterfactual public condition is
diagnostic evidence, not an admitted task. Do not call a predicate-only probe a product run, do not
infer rejection from a timeout, an unavailable tool or an unaccepted submission, and keep any
private construction in investigator evidence rather than in a future Builder or reviewer prompt.

## Keep what was seen apart from why

Every finding carries two sentences that are easy to fuse: what the recorded bytes show, and the
cause you infer from them. Write them separately. The operator can then keep an observation that is
certainly true while rejecting a cause that is only plausible, and the next investigation inherits
the observation without inheriting the guess. "Eighteen of twenty-five cases passed and no check
failed in shipping" is an observation; "the checks were too weak" is one cause and "the tasks were
too easy" is another, and the lane that separates them is the evidence, not the sentence that
names one.

## Reconcile disagreements by method

When lanes disagree, compare their instruments before their verdicts. Did they read the same bytes,
execute the same layer and cover the same families? Did either reuse the proposed answer, read its
counterpart or look at hidden truth before judging? Did the "independent" checker actually run, and
can its adapter represent this artifact? An honest unobservable result often identifies the
instrument missing behind a confident claim, and neither confidence nor a majority vote decides
correctness.

Reconcile lane 23's trace challenge with lane 22's process reading explicitly, since they read the
same traces under different rules, and lane 7's valid alternatives separately from the
wrong-artifact discrimination of row E and lane 6. Two reports may describe one mechanism at
different depths; collapse them under one owner. When no available observation separates the
accounts, state the unresolved alternatives plainly.

When a premise falls, walk forward through everything built on it — a fix, a hardness claim, a
cost claim, a comparison — and withdraw those conclusions explicitly, including your own earlier
ones and any in a handover. Then name what survives on independent evidence. Valid sampled
artifacts do not refute a demonstrated ability to accept an invalid one, and a verifier gap does
not prove the recorded cases exploited it.

## Compare change without manufacturing a trend

Write down what stayed fixed and what moved between the compared batteries or runs: source,
Builder, Built model, reviewer, harness, verifier, tasks and environment are separate conditions. A
rebuilt product can raise its score while changing what the score means. Credit a useful recovery
while leaving its cause open when several owners moved together, and keep more completed
measurement, fewer operational failures and better verification as three improvements rather than
one scalar.

For an exact repeat, pair cases by recorded identity and report both directions of change; one
pair shows variability without establishing a noise threshold. Never pool harness generations into
one capability denominator, and when a run stopped before measurement, compare coverage and source
rather than scores that do not exist. For a climb, keep the Builder's `EXPERIMENT.json`, the
controller's difficulty decision and the realised task bytes apart; [the climb reference](climb.md)
says which record holds what. Unchanged outcomes do not mean unchanged difficulty, since the old
solutions may still suffice, and a changed public field proves no harder work when the deciding
check ignores it.

## Judge tools by the work they enable

Separate available tools, eligible opportunities, actual use, successful use and decision-changing
use. An unused tool may lack opportunity, be poorly described, be redundant or solve the wrong
problem, and the traces and implementation choose between those rather than a usage rank. Fewer
turns, more calls and uniform sequences measure no intelligence by themselves; look instead for
revisions, search, repair, carried state and the quality of the submitted artifact.

The solver's tools are also the Builder's, so read what each returns as well as how often it was
called. A tool that reports every margin a check reads lets a solver propose, read the failing
state and adjust, which evaluates candidates and synthesises none; lane 34 reads that. For the
Builder's own tools, read native Bash patterns as demand evidence: what was it repeatedly trying to
obtain, and could an existing tool have produced that with less work? A repeated workaround across
independent builds is stronger evidence than one failed command followed by productive work.

## Ask what each reviewer contributed

Trace finding, delivered feedback, recipient action and next eligible measurement. An attached
diagnosis is evidence of delivery, not of a useful repair, and a reviewer can add value by
preserving uncertainty without controlling routing. The Epoch Reviewer reviews twice: the
authoring review runs during the round and `holdSubmit` holds submit on its `join()`, so its
findings reached the Builder before the battery, and the battery review reads the measured tree
afterwards. Credit or fault each separately.

Judge agreement is not independence. The Main Judge reads the Builder's public rules and the
artifact, so when it agrees with a verifier pass, it has read the same rules a second time, and a
fault both miss is invisible to both. A handful of Judge fails is a sample of what the Judge
noticed, not a sample of false accepts, and a battery with no disagreement may simply have no fault
the Judge could see. Model agreement creates no independence when the model and its premises are
shared, and removing or expanding a reviewer deserves evidence about useful information per
opportunity rather than a count of criticisms.

## Ask whether this has happened before

Before proposing a remedy, read the earlier notes under `notes/` for the same mechanism. A
mechanism that recurs has usually been found before, and its remedy is often already in the source
as a standing duty of one component: a reviewer prompt line, a gate, a sensor. So the first
question is whether that duty fired in this run. A duty that ran and found nothing, a duty that
found the mechanism and routed it nowhere, and a duty that never ran are three findings, and only
the first asks for a different remedy. Lane 12 reads the Epoch Reviewer's duties and lane 14
follows the finding. When the earlier fix is in the measured source and the mechanism recurred
anyway, say so in one sentence with the commit, and name the recurrence so the next reader finds
both notes.

## Turn findings into useful next actions

Keep the four evidence levels apart — present in source, deterministically proved,
live-exercised, outcome-proved — and inspect a repair's commit and ancestry before calling it
current. A later fix cannot improve what an older run proved. Prefer the smallest further
observation that would change the proposed action, and when none remains in scope, finish.

Give each proposal one owner, a concrete changed behaviour and a falsifier, and prefer an existing
operation or shared contract over another observer or instruction layer. Use the three final
sections. A **Patch** is a small correction the deciding evidence already supports. A
**Consolidate** chooses the one authority duplicated representations should derive from and names
what disappears. An **Overhaul** states the broader simplifying contract and what it replaces. When
nothing is justified at one level, say so. Keep review proposals apart from the operator's decisions
about spend, promotion, continuation and scope; WRI supplies evidence, and the campaign owns
promotion, backtracking and new run authority. Project frozen predictions and campaign events
without changing their words, and give a quiet safeguard an opportunity denominator before calling
it successful or obsolete.

## Finish a readable synthesis

Write a causal account rather than a transcript of the investigation. Put the strongest finding
early and the detail beside the claim it supports, use tables for compared conditions, counts and
evidence levels, and keep an alternative explanation only when it materially limits the conclusion.
The synthesis adjudicates once, the reports preserve research and the digest preserves counts, so
no second handoff ledger is needed to drift from them.

Before delivery, revisit the weakest consequential inference. Was the named command executed? Did
the actual consumer run? Did a source-only claim turn into a live claim, or a Builder-authored check
into an independent one? If a quick receipt or source check would change the queue, do it now. Then
inspect the publication for protected detail and stale handover prose, and run the archive
validator, remembering that it proves shape and bindings and not that the prose is true.

Keep this reference at roughly two hundred to three hundred lines. That is a writing nudge rather
than a gate, so keep a necessary explanation rather than game the count, and apply the same
judgement to the synthesis: enough evidence to assess the decision, and little repeated machinery.
