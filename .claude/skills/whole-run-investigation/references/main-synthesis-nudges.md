# Main synthesis: judgement nudges

Use this when turning WRI evidence and lane reports into `main_synthesis.md`.
It guides the primary reviewer; it adds no runtime gate or campaign authority.
Read the questions that matter to this run. Do not perform every possible investigation.
Aim to settle the decisions the evidence can settle, then deliver the useful remainder honestly.

## Start from the operator's decision

What is the operator trying to decide after this review?
Usually it is whether a product works, what limited it, what changed, or which repair is worth trying.
Let that question determine the synthesis, rather than the order in which reports arrived.
Keep the exact short domain prompt in view: a convenient generated subproblem may underserve it.
Do not silently turn a request for broader capability into a search for a higher score.

Begin with the measured source identity and the [product-flow checklist](../CHECKLIST.md).
Then give the consequential conclusion in ordinary language, with its strongest supporting evidence.
Explain what a capable user can rely on and the specific condition that still limits that reliance.
“Not universally proved” is rarely a useful finding; name the concrete missing or adverse evidence.
One credible counterexample can settle a defect without estimating its prevalence.
A finite collection of successful cases can support a bounded capability without guaranteeing every use.

## Recover before restarting

Check existing manifests, report files, snapshots and session terminals before buying another review.
A resumed session should finish the accepted work rather than rerun everything after compaction.
Retain complete reports, including opinions later rejected, under the existing archive contract.
Distinguish a recovered report from a verified transport identity or a still-running session.
Missing historical transport receipts limit provenance; they do not erase inspectable primary evidence.
Conversely, a session id or successful process exit does not supply a missing report.

Use subagents only when authorised and when a bounded unresolved judgement benefits from independence.
Do the deterministic joins once in the primary session with the owning readers.
Keep the two sides of an independent challenge separate until both return.
If a lane is missing, name the missing work; replace only coverage that still affects the decision.
The catalogue is rows A to I and twenty-eight lanes; an older note that names an angle by a retired
number is carrying a mechanism, so translate the mechanism to the lane that owns it today.
WRI's skill and archive validator own the required shape; this reference does not invent another one.

## Bind the evidence that decides

Read the opening's full source SHA and distinguish it from the analyst's and procedure's revisions.
Follow the saved candidate, accepted snapshot, executed bundle and task-set identities.
Workspace Git is useful attribution; it is not a substitute for the bytes actually accepted and run.
A later file with the same name can describe a different harness generation.
When a live run advances, refresh affected evidence and preserve findings whose identities still match.
Two post-terminal snapshots establish stable reads, not observation of a live transition.

Keep operational closure separate from capability evidence.
Partition verified, unaccepted and typed non-result cases before reporting rates.
A pre-submit stop can leave substantial filesystem work and still have no measured harness.
Read the partial work if it can settle a concrete authoring dead end; avoid treating it as accepted.
An environment terminal can be informative without becoming a failed domain solution.
A signal or quota stop does not erase verdicts already recorded earlier in the run.

Name the denominator beside each inference, not just in a distant accounting section.
Cases, batteries, author calls, candidate submits, completed rounds and provider units differ.
Do not use a shared provider ceiling as a local turn limit without explicitly disclosing the distinction.
When a legacy archive field cannot express a fact, state that limitation rather than invent a receipt.
Treat unavailable costs, model identities and opportunities as unknown, not zero.
Validate bookkeeping; do not allow a well-formed archive to stand in for a sound conclusion.

## Find the consumer, not only the calculation

For a consequential claim, follow the short path from input bytes to the deciding output.
What receives the artifact, what computes a result, and what does the controller finally consume?
Look for filtering, projection, substitution, applicability and preprocessing between those points.
An evaluator can reject while a later deciding predicate accepts, or the reverse.
A prompt assertion, schema type or passing helper test proves only the layer it reaches.
Ask whether the report executed the same consumer that made the recorded decision.

Consider both a defect and a legitimate division of authority.
Generated diagnostics may intentionally be advisory while a host check owns correctness.
In that case, fix the incorrect declaration or binding rather than granting diagnostics new authority.
A valid boundary can expose a product defect without itself being the defective boundary.
Check callers before naming one owner: a local symptom may have a single shared producer.
Stop tracing when you can name the deciding line, its contract and the affected decision.

If a cheap replay can separate explanations, execute it in private scratch against the measured layer.
Use the recorded public input and accepted artifact where they fit the question.
Pair the relevant hostile probe with a positive or nearby control so the result has an interpretation.
State whether the probe changes the artifact, the public condition, or both.
A counterfactual public condition is diagnostic evidence, not a newly admitted task.
Preserve source and bundle identities and keep controller-generated output unchanged.

Do not call a predicate-only probe a full product run when an external check was omitted.
Do not call a generated evaluator probe a host-verdict replay when its issues are replaced later.
Do not infer rejection from a timeout, unavailable tool or unaccepted submission.
Use a stand-in only with its limits stated; it cannot prove the missing practitioner's tool worked.
A private construction belongs in investigator evidence, not in future Builder or reviewer prompts.
The archive can retain the method, safe counts and digests without exposing protected payloads.

## Reconcile disagreements by method

When lanes disagree, compare their instruments before comparing their verdicts.
Did they inspect the same bytes, execute the same layer and examine the same families?
Did either reuse the proposed answer, read its counterpart or inspect hidden truth before judging?
Did an “independent” checker actually run, and can its input adapter represent this artifact?
An honest unobservable result often identifies the missing instrument behind a confident claim.
Do not average confidence or use a majority vote to decide correctness.

Reconcile lane 23's trace challenge with lane 22's process reading explicitly, since they read the
same traces under different rules; assess lane 7's valid alternatives separately from the
wrong-artifact discrimination that row E and lane 6 report.
For each material disagreement, give methods, samples, the deciding evidence and the surviving scope.
Two reports may describe one mechanism at different depths; collapse them under one owner.
Two compatible counts may use different projections, such as whole artifacts and member assignments.
Make that distinction before labelling the data inconsistent.
If no available observation separates the accounts, state the unresolved alternatives plainly.

When a premise falls, walk forward through the conclusions built on it.
Which fix, hardness claim, cost claim or comparison depended on that premise?
Withdraw those conclusions explicitly, including any in your own earlier messages or handover.
Then name what survives on independent evidence.
For example, valid sampled artifacts do not refute a demonstrated ability to accept an invalid one.
Likewise, a verifier gap does not prove agents exploited it in the recorded cases.

## Compare change without manufacturing a trend

Write down what stayed fixed and what changed between the compared batteries or runs.
Source, Builder, Built model, reviewer, harness, verifier, tasks and environment are separate conditions.
A rebuilt product may improve its measured score while changing the meaning of that score.
Credit useful recovery while keeping its cause unresolved when several owners moved together.
More completed measurement, fewer operational failures and better verification are distinct improvements.
Do not demand that every useful observation fit one scalar success rate.

For an exact repeat, pair cases by recorded identity and report both directions of outcome changes.
One repeat pair demonstrates observed variability; it does not establish a general noise threshold.
An interval describes its stated sampling assumptions, not independence that the run did not provide.
Do not pool different harness generations into one capability denominator.
When a run stops before measurement, compare live coverage and source changes, not nonexistent scores.
“No measurement opportunity” is more useful than declaring an unexercised fix successful or failed.

For a climb, separate the Builder's `EXPERIMENT.json` target, the controller's recorded
difficulty decision and the realised task bytes; the [climb reference](climb.md) says which record holds each.
Read actual predecessor links instead of trusting adjacent filenames or a convenient reader projection.
Check the changed public input against the declared axis and the deciding constraint.
Unchanged families may be deliberate controls; preserve them while isolating the moved-family evidence.
Unchanged outcomes do not alone mean unchanged difficulty: the old solutions may still be sufficient.
Conversely, a changed public field cannot prove harder verified work when the deciding check ignores it.

## Judge tools by the work they enable

Separate available tools, eligible opportunities, actual use, successful use and decision-changing use.
An unused tool may lack opportunity, be poorly described, be redundant, or solve the wrong problem.
Choose among those explanations from traces and implementation rather than usage rank alone.
Low use is neither a reason to delete a tool nor a reason to expand it until it is used.
Fewer turns, more calls and uniform sequences do not independently measure intelligence.
Look for revisions, parameter search, repair, state carry and the quality of the submitted artifact.

Inspect native Bash patterns as demand evidence where requests are recorded.
What result was the Builder repeatedly trying to obtain: inspect, compare, edit, preview, verify or recover?
Could an existing custom tool have produced that result with less repeated work?
If yes, inspect its discoverability, argument shape and return value before adding another tool.
If no, consider extending the nearest coherent tool, consolidating duplicates or retaining Bash's flexibility.
The target is a useful operation with a clear result, not a preferred total number of tools.

Distinguish exploratory scripts from recurring friction and from unsafe or incorrect operations.
One failed shell command followed by productive work may need no system change.
A repeated workaround across independent builds is stronger demand evidence.
Check whether a proposed tool returns actionable public information without crossing the truth boundary.
Compare time and cost at their reported scopes; tiny tool latency may not explain a slow model turn.
If successful Bash requests are missing, report the observation gap instead of reconstructing intentions.

## Ask what each reviewer contributed

Trace finding → delivered feedback → recipient action → next eligible measurement.
An attached diagnosis is evidence of delivery, not proof of a useful repair.
A reviewer can add value by preserving uncertainty or challenging verification without controlling routing.
Compare the component against its actual contract, including when it is intentionally advisory.
Do not turn a retired component into an unused live mechanism because an old reader still names it.
A skipped unchanged condition differs from a missed fresh opportunity.

Check calibration and standing at the exact decision where they matter.
No disagreement may legitimately mean no paid calibration under the current policy.
An issue should not become fixed merely because an unvalidated reviewer could not sustain it.
Model agreement does not create independence when the same model and assumptions are shared.
Separate measured provider units from money and total campaign cost from one reported subset.
Removal or expansion deserves evidence about useful information per opportunity, not criticism counts.

## Ask whether this has happened before

Before proposing a remedy, read the earlier notes under `notes/` for the same mechanism.
A mechanism that recurs across runs has usually been found before, and its remedy has often already landed.
That remedy is frequently a standing duty of one component: a sentence in the Epoch Reviewer's prompt, a gate, a sensor.
So the first question is not what to propose but whether the standing duty actually fired in this run.
Read the recorded reviews or the sensor's log and say whether the duty was invoked, what it found, and where the finding went.
Lane 12 reads the Epoch Reviewer's duties that way and lane 14 follows the finding; take their reports before answering from the primary.
A duty that ran and found nothing, a duty that found the mechanism and routed it nowhere, and a duty that never ran are three different findings.
Only the first of those asks for a different remedy; the other two ask why the existing one did not reach a decision.
A second remedy for a mechanism whose first one never ran adds a wall that pays no rent.
When the earlier note's fix is in the measured source and the mechanism recurred anyway, say so in one sentence, with the commit that carried the fix.
Name the recurrence in the synthesis as a recurrence, so the next reader finds both notes.

## Turn findings into useful next actions

Keep the four evidence levels distinct: present, deterministically proved, live-exercised, outcome-proved.
Before calling a repair current, inspect its actual commit and ancestry into the intended tree.
A later fix cannot improve what an older run proved; a merged fix still needs its relevant live branch.
An existing green positive/hostile check can be sufficient deterministic proof: do not rerun it ceremonially.
Prefer the smallest additional observation that would change the proposed action.
If no such observation remains within scope, finish rather than indefinitely requesting more evidence.

Give each proposed change one owner, a concrete changed behaviour and a falsifier.
Prefer an existing operation or shared contract over another observer, registry or instruction layer.
Name which duplicated fact or obsolete path disappears when proposing consolidation.
Do not retain a mechanism merely because keeping it feels safe; explain its actual purpose.
Do not propose an overhaul merely because the review format has a heading for it.
Describe the simplifying contract that would prevent the demonstrated class of failure.

Use the existing final sections: Patch, Consolidate, Overhaul.
A patch is a small correction already supported by the deciding evidence.
A consolidation chooses the one authority from which duplicated representations should derive.
An overhaul states the broader simplifying contract and what it would replace.
When no item is justified at one level, say so rather than filling the section with speculative work.
Separate review proposals from operator decisions about spend, promotion, continuation and scope.

Project frozen predictions and existing campaign events without changing their words or authority.
If a likely refutation lacks campaign backtracking, retain it as advisory and name the pending owner.
Quiet safeguards need an opportunity denominator before being called successful or obsolete.
T0/T1 log coverage alone does not prove that each sensor had an eligible opportunity.
WRI supplies evidence; the campaign owns promotion, backtracking, retirement and new run authority.
These boundaries remain in force even when a better next experiment seems obvious.

## Finish a readable synthesis

Write a causal account, not a transcript of investigations or a tour of every file read.
Keep the strongest finding early and put detail next to the claim it supports.
Use tables for compared conditions, counts, evidence levels and changed decisions.
Keep alternative explanations when they materially limit the conclusion; discard decorative caveats.
Let the main synthesis adjudicate once, the reports preserve research, and the digest preserve counts.
Avoid a second handoff ledger that will drift from the four-file archive.

Before delivery, revisit the weakest consequential inference.
Was a named command executed? Did the actual consumer run? Did a source-only claim become a live claim?
Would a quick receipt or source check change the queue? If so, do that check now.
Then inspect the publication for protected detail and stale contradictory handover prose.
Run the existing archive validator; disclose historical gaps it cannot settle.
A successful validator proves shape and bindings, not scientific validity or complete runtime provenance.

Keep this protocol roughly 200–300 lines and below about 5,000 tokens when editing it.
Those are writing nudges, not gates; preserve a necessary explanation rather than gaming the count.
Use the same judgement for the report: enough evidence to assess the decision, little repeated machinery.
Leave the operator with the useful conclusion, the exact next discriminator and a finished archive.
